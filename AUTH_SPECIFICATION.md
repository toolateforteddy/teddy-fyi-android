# Blueprint: Authentication Flow & API Integration

This document defines the authentication protocol for the Teddy FYI Android client and its interaction with the `api-rust.teddy.fyi` backend.

## 1. Overview
The system uses Google Identity for initial authentication, which is then exchanged for backend-specific JWT access and refresh tokens. All subsequent API calls are authenticated using these JWTs.

## 2. Authentication Endpoints

### **Login / Token Exchange**
Used to exchange a Google ID Token for application-specific tokens.
- **Endpoint**: `POST https://api-rust.teddy.fyi/auth/login`
- **Request Body**:
```json
{
  "user_id": "string (Google User ID)",
  "client_uuid": "string (UUID generated by client)",
  "google_auth_token": "string (Google ID Token from androidx.credentials)"
}
```
- **Response Body (200 OK)**:
```json
{
  "access_token": "string (JWT)",
  "refresh_token": "string (Long-lived UUID or JWT)"
}
```

### **Token Refresh**
Used when the `access_token` has expired.
- **Endpoint**: `POST https://api-rust.teddy.fyi/auth/refresh`
- **Request Body**:
```json
{
  "user_id": "string",
  "client_uuid": "string",
  "refresh_token": "string"
}
```
- **Response Body (200 OK)**:
```json
{
  "access_token": "string",
  "refresh_token": "string"
}
```

## 3. Request Headers
Every authenticated request MUST include the following headers:

| Header | Value | Purpose |
| :--- | :--- | :--- |
| `Authorization` | `Bearer <access_token>` | Identifies the user session. |
| `X-Client-UUID` | `<client_uuid>` | Identifies the specific device/installation. |
| `Content-Type` | `application/json` | Mandatory for all POST/PUT requests. |

## 4. Secure Token Storage
Tokens must NEVER be stored in plain text (e.g., standard `SharedPreferences`). 

### **Implementation: EncryptedDataStore**
The client uses `androidx.datastore` combined with Android's `KeyStore` system for encryption.
- **Access Token**: Encrypted and stored locally.
- **Refresh Token**: Encrypted and stored locally.
- **Client UUID**: Stored to maintain session consistency across refreshes.

## 5. Token Lifecycle & Refresh Mechanism
The client implements an automatic refresh interceptor using Ktor's `Auth` plugin:

1.  **Detection**: If a request returns a `401 Unauthorized`, the client intercepts the response.
2.  **Renewal**: The client automatically calls the `/auth/refresh` endpoint using the stored `refresh_token`.
3.  **Retry**:
    - If refresh succeeds: The new `access_token` is saved, and the original failed request is retried with the new token.
    - If refresh fails (e.g., `403 Forbidden` or refresh token expired): The user is logged out, and local session data is cleared.

## 6. Obtaining Google Tokens
The client uses the `androidx.credentials` library to facilitate one-tap sign-in.

### **Workflow**
1.  Initialize `GetCredentialRequest` with `GetGoogleIdOption`.
2.  Set the `webServerClientId` to the backend's Google Client ID.
3.  Call `credentialManager.getCredential()`.
4.  Extract the `idToken` from the result and pass it to the `login` endpoint described in Section 2.

## 7. Security Best Practices
- **Short-lived Access Tokens**: The backend should issue access tokens with short expiry (e.g., 15-60 minutes).
- **Refresh Token Rotation**: Each refresh call should ideally return a new refresh token, invalidating the old one.
- **SSL Pinning**: (Optional/Future) Implement SSL pinning for `api-rust.teddy.fyi` to prevent MITM attacks.
